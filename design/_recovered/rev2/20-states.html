States

Loading, empty, error and degraded are where a product stops feeling finished, and they are always the ones left out of a design file. They are specified here because this codebase has a recurring bug — catch { setX([]) } — that renders a failed request as an empty list. That is a design problem before it is a code problem: if the empty state is the nicest-looking thing in the file, it is what gets reached for.

1 · Loading — content uses a skeleton

Open positionsloading

Content loads with a skeleton in the shape of the content. An action spins. The skeleton reserves the exact row grid so nothing jumps when data lands — a table that reflows on arrival is how a trader mis-clicks a position. 2 · Empty — nothing is wrong, there is simply nothing

✓

Clean session

Eight trades, no behavioural flags. Your pace, sizing and cooldowns all stayed inside what you set.

Journal · todayempty
✎

Nothing written yet

How you are trading today, and what you plan to do about it. Two lines is enough.

An empty state names what is absent and offers the one action that fills it. “Clean session” is a result, not a blank — it earns a green tick because zero alerts across eight trades is genuinely the good outcome. An empty state never takes an error colour and never gets a retry button; if there were something to retry, it was not empty.

You are offline

Showing the last snapshot from 13:41. Prices and P&L are frozen until the connection comes back.

reconnecting · attempt 3

Three things an error state must carry: what failed in the user's language, whether their data is at risk, and a way out. The endpoint and timestamp go in mono in an inset well — a trader will paste that line into a support email and it saves a round trip. Offline is an error, not an empty, and it names the snapshot you are looking at, because a frozen P&L presented as live is the most expensive lie this interface could tell.

4 · Degraded — the page works, one guarantee does not

Prices are delayed. The market-data feed dropped at 13:38. P&L below is computed from the last tick received, not live. Details
Syncing your trades. 142 of 380 fills imported. Analytics will be incomplete until this finishes. 42%
Demo mode — showing sample data. Nothing here is your trading. Connect Zerodha to replace it. Connect Zerodha

Degradation is announced inline, above the thing that is degraded, and never as a toast. A toast saying prices are stale is gone by the time the trader looks at the price. The banner stays as long as the condition does, and states the consequence (“P&L is computed from the last tick”) rather than the cause (“websocket disconnected”).

The rule

A failed request is never rendered as an empty state. Empty means the server answered and the answer was nothing. Error means the server did not answer. Those are different facts about the world and a trader acts on them differently — one says “you had a clean session”, the other says “you do not know what your session was”. Any component that can show both must take them as separate props, never as one nullable array.

There is a third case this codebase keeps hitting: a component that returns null when its data is missing, so a failed request renders as nothing at all — no card, no header, no space. That is worse than a wrong empty state, because there is nothing on screen to be suspicious of. If a section has a header, the header renders even when the body cannot.
