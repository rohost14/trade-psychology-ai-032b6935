States

The four states below are where a product stops feeling finished, and they are always the ones left out of a design file. They are specified here as components because this codebase has a recurring bug — catch { setX([]) } — that renders a failed request as an empty list. That is a design problem before it is a code problem: if the empty state is the nicest-looking thing in the file, it is what gets reached for.

1 · Loading — content uses a skeleton

Open positionsloading

Content loads with a skeleton in the shape of the content. An action spins. The skeleton reserves the exact row grid so nothing jumps when data lands — a table that reflows on arrival is how a trader mis-clicks a position. A spinner is only ever attached to a control the user pressed:

2 · Empty — nothing is wrong, there is simply nothing

✓

Clean session

Eight trades, no behavioural flags. Your pace, sizing and cooldowns all stayed inside what you set.

Journal · todayempty
✎

Nothing written yet

How you are trading today, and what you plan to do about it. Two lines is enough.

An empty state names what is absent and offers the one action that fills it. “Clean session” is a result, not a blank — it earns a green tick because zero alerts on eight trades is genuinely the good outcome. An empty state never gets an error colour and never gets a retry button; if there is anything to retry, it was not empty.

3 · Error — always distinguishable from empty

!

The request failed after one automatic retry. Your trades are safe — this is a read, and nothing was written.

GET /api/analytics/behaviour · 500 · 14:22:07

Positionsoffline
⚡

You are offline

Showing the last snapshot from 13:41. Prices and P&L are frozen until the connection comes back.

reconnecting · attempt 3

Three things an error state must carry: what failed in the user’s language, whether their data is at risk, and a way out. The endpoint and timestamp go in mono at the bottom — a trader will paste that line into a support email and it saves a round trip. Offline is an error, not an empty, and it says which snapshot you are looking at, because a frozen P&L presented as live is the most expensive lie this interface could tell.

4 · Degraded — the page works, one guarantee does not

Prices are delayed. The market-data feed dropped at 13:38. P&L below is computed from the last tick received, not live. Details
Syncing your trades. 142 of 380 fills imported. Analytics will be incomplete until this finishes. 42%
Demo mode — showing sample data. Nothing here is your trading. Connect Zerodha to replace it. Connect Zerodha

Degradation is announced inline, above the thing that is degraded, and never as a toast. A toast that says prices are stale is gone by the time the trader looks at the price. The banner stays for as long as the condition does, and it states the consequence (“P&L is computed from the last tick”) rather than the cause (“websocket disconnected”).

The rule

A failed request is never rendered as an empty state. Empty means the server answered and the answer was nothing. Error means the server did not answer. Those are different facts about the world and a trader will act on them differently — one says “you had a clean session”, the other says “you do not know what your session was”. Any component that can show both must take them as separate props, not as one nullable array.
