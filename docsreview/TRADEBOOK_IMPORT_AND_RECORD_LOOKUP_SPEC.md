# Tradebook Import + "What's My Record Here?" — Spec

Status: **PROPOSAL — not approved, not started.** Written 2026-07-23.
Supersedes the Blowup Shield "Pact" concept (parked — see §0.2).

---

## 0. Why these two, and why in this order

### 0.1 The constraint that forces this (VERIFIED)

Kite Connect cannot give us trade history. From the official docs
(https://kite.trade/docs/connect/v3/orders/):

> "This API returns a list of all trades generated by all executed orders **for the day**."
> "The order history or the order book is transient as it **only lives for a day** in the system."

`zerodha_service.get_trades()` calls `GET /trades`. There is no backfill anywhere
in `trade_sync_service`. **Consequence: a new subscriber connects and we know
nothing about them.** History only accrues forward from the day they sign up.

Measured on the live DB (2026-07-23):

```
completed_trades         157
accounts with trades      58     -> ~2.7 trades per account
risk_alerts               55
alerts with user outcome   0
```

Two conclusions:

1. **Every history-dependent feature is empty at signup.** Analytics, Edge/Leak,
   My Patterns, quality scores, Trade DNA. A paying user sees empty cards for
   weeks. This is very likely a bigger driver of "Analytics feels too advanced"
   than jargon is — the page is not just complex, it is *blank*.
2. **Zero adoption of the alert feedback loop.** Migration 069 shipped
   `stopped / took_anyway / not_useful` buttons. 55 alerts, 0 outcomes recorded.
   **Design rule going forward: features must require no manual user input.**

### 0.2 What this parks

The "Pact" idea (attach a written *why* to each Constitution rule, quote it back
during the hot state) is behaviourally well-supported but rests entirely on users
typing a reason. A cohort that has never tapped a single one-tap feedback button
will not write prose. Parked until there is evidence of input willingness.

### 0.3 Order

Import first. The lookup is worthless without history, and so is most of the
existing product. Import is the unlock; the lookup is the payoff.

## 1. Feature A — Tradebook Import

**One line:** let the user upload their Zerodha Console tradebook and instantly
populate months or years of real trading history.

### 1.1 Why it is the highest-leverage item on the board

It is not a feature so much as the precondition for the features already built.
The day it ships, Analytics has data, Edge/Leak finds real leaks, My Patterns has
a real scorecard, quality scores stop being noise, and the record lookup in
Feature B becomes possible. The user reaction we are chasing — *"it already knows
my last two years"* — comes from here, and it costs one endpoint and a parser.

### 1.2 Source data (verified)

Zerodha Console → Reports → Tradebook. CSV and XLSX. Arbitrary custom date range.
Segments: equity, F&O, commodity, currency.

Documented columns (confirmed across two independent sources):

| Field | Notes |
|---|---|
| Trade Date | execution date |
| Symbol / tradingsymbol | instrument |
| Exchange | NSE / BSE / NFO / MCX / CDS |
| Segment | equity / FO / etc. |
| Trade Type | buy / sell |
| Quantity | |
| Price | |
| Order ID | |
| Trade ID | broker-unique |

**Exact header casing/spelling is NOT publicly documented and has changed
historically.** The parser must therefore be tolerant, not literal — see §1.4.

### 1.3 Endpoint

```
POST /api/account/import-tradebook     multipart/form-data, file=<csv|xlsx>
GET  /api/account/import-tradebook/{job_id}    -> progress/result
```

Auth: standard `get_verified_broker_account_id`. Rate limit: 3/hour.
Max upload: 10 MB. Reject anything else by content sniff, not extension.

Large files must not block the request — parse synchronously only if the row
count is small, otherwise hand to Celery and poll. (Suggest: inline under 2,000
rows, queued above.)

### 1.4 Parser requirements

- **Header detection by scan, not fixed offset.** Console exports have carried
  metadata/banner rows above the table at various times. Scan the first ~20 rows
  for the one that looks like a header (contains a date-ish column AND a
  quantity-ish column).
- **Alias map + normalisation.** Lowercase, strip, collapse whitespace and
  underscores, then map: `trade date|trade_date|date` → `trade_date`;
  `symbol|tradingsymbol|instrument` → `tradingsymbol`;
  `trade type|type|buy/sell|transaction type` → `transaction_type`; etc.
  Unknown columns are ignored, never fatal.
- **Idempotency on `trade_id`.** Re-uploading an overlapping range must not
  duplicate. Unique index on `(broker_account_id, broker_trade_id)`, insert with
  `ON CONFLICT DO NOTHING`. This is the single most important correctness
  property — users *will* upload overlapping ranges.
- **Timezone.** Console dates are IST. Convert to UTC on write; the rest of the
  codebase stores UTC and localises with `_IST` at read time.
- **Product filter.** Existing rule: MIS/NRML/MTF only, no CNC. Console may not
  expose product per trade — if absent, infer from segment, and record what was
  inferred rather than guessing silently.
- **Never trust the file.** Cap rows (e.g. 200k), validate types per row, collect
  per-row errors into a report instead of aborting the whole import.

### 1.5 After ingest

Imported fills land in `trades`, then must run the same pipeline live sync uses:

1. FIFO round-trip construction → `completed_trades`
2. `completed_trade_features` computation
3. Strategy-group detection

Do **not** run the behaviour engine over imported history to emit alerts —
back-dated alerts would be noise and would corrupt the alert timeline. Imported
data is for analytics and the record lookup only. (Explicit decision; revisit
separately if we ever want retro-pattern detection, which is a different feature
with different UX.)

P&L stays **raw** per the standing rule — `(exit-entry)*qty*multiplier`, no
charges, ever.

### 1.6 UI

Settings → Danger Zone already owns export. Import belongs next to it, or in its
own "Your data" section. Needs:

- drag/drop + file picker
- link and short instructions for getting the file from Console
- progress, then a result summary: rows read, trades imported, duplicates
  skipped, rows rejected (downloadable error list)
- explicit note that imported history powers Analytics but does not generate
  back-dated alerts

### 1.7 Risks

| Risk | Mitigation |
|---|---|
| Console format changes | tolerant parser (§1.4); fail with a clear "unrecognised format" and the headers we saw, not a stack trace |
| Duplicate uploads | `ON CONFLICT DO NOTHING` on `(account, broker_trade_id)` |
| Huge file OOM | stream-parse, row cap, Celery for large jobs |
| Wrong-account upload | tradebook contains the client ID; if present, compare to `broker_user_id` and refuse on mismatch |
| Multiplier/lot-size errors on old F&O symbols | reuse existing `mcx_contract_specs` + instrument parser; divergences already land in `data_quality_events` (migration 070) |

## 2. Feature B — "What's My Record Here?"

**One line:** a searchable, situational lookup of the user's own real trading
record for the instrument they are about to trade.

### 2.1 The gap (researched)

Journals cover this **post-hoc**, as passive insight cards you read on a Sunday.
TradesViz will say *"win rate improves from 35% to 68% when you wait until 10 AM"*.
Tradewink breaks win rate down by setup and regime. Edgewonk, TradeZella,
Tradervue, TraderSync all do variations.

**None ship it as a pre-trade lookup you consult at 2pm with your finger over the
buy button.** That is the gap: not the statistic, the *moment*.

Competitively it is also defensible:
- **Sensibull** models the option (payoff, greeks, expiry). It does not know you.
- **Zerodha Nudge** is real-time but platform-authored and generic — concentration,
  T2T, ETF premium. Not personal history.
- **Tijori** is the shape we are copying (search → full report), applied to the
  one dataset only we hold: the user's own behaviour.

### 2.2 What it is not

- Not a prediction. Not a counterfactual. Not "this would have saved you ₹X".
- **Not the what-if simulator** that was previously rejected — that modelled a
  hypothetical price move. This reports trades that actually happened.
- Passes the standing analytics filter: factual, provable, differentiated.

### 2.3 Shape

```
NIFTY 25000 CE — you have traded this 47 times

  This hour (2-3pm):  12 trades · 25% win · -₹18,400     <- your worst window
  Mornings (9-11am):  19 trades · 63% win · +₹22,100
  Longest hold ever:  40 min
  After 2+ losses:    3 trades · 0 wins
```

Plus one plain-language verdict line derived from the strongest signal present.

### 2.4 Situational slices

Aggregate-only is what Analytics already does. The value here is *now*:

- current hour bucket
- today's state: trades so far, consecutive losses (both already available from
  `/api/danger-zone/status`)
- direction / option type
- weekday, expiry-day flag

### 2.5 Sample-size handling — the make-or-break detail

`instrument × hour × state` will frequently be under any sane threshold.
Edge/Leak already gates at `MIN_TRADES = 5`.

**Widen automatically and say which bucket is being shown.** Cascade:

```
instrument + hour + state  ->  instrument + hour  ->  instrument
   -> underlying + hour     ->  underlying        ->  "not enough data yet"
```

Always label the level ("across all your NIFTY trades" vs "NIFTY CE at 2pm").
Never present a 2-trade bucket as if it were an edge. Never silently widen.

### 2.6 What already exists (~60%)

`GET /api/analytics/instrument?underlying=&days=` already returns per-underlying
KPIs, `by_option_type`, `by_hour`, equity curve and recent trades.
`InstrumentPanel.tsx` renders it.

Missing:
1. **A way in.** Today it is only reachable by clicking a bar inside
   Analytics → Edge. It needs to be a destination: nav item and/or search box,
   and ideally reachable from an open position on the Dashboard.
2. **Situational slicing** (§2.4) — currently aggregate only.
3. **The cascade + labelling** (§2.5).
4. **A verdict line** in plain language.

### 2.7 Where it lives

Strong candidate: **this is what Blowup Shield should become.** It replaces a
confused page (which duplicates the Alerts page's "did you listen" story with a
weaker inferred signal) with a genuine utility. The one asset worth keeping from
today's Shield — the post-alert timeline as *evidence* — can move to Alerts,
which owns the alert loop per the page-ownership split.

---

## 3. Sequencing

1. **Tradebook import** — without it, B has nothing to read and the existing
   product stays empty for new users.
2. **Record lookup** — retire/absorb Blowup Shield in the same pass.

Both are additive. Neither needs new detectors or engine work.

## 4. Open questions for the user

- Import: Console CSV only to start, or XLSX too? (CSV is simpler and Zerodha
  recommends it for data work; XLSX needs `openpyxl`.)
- Should imported history be visible in Journal (it has no journal entries), or
  analytics-only?
- Does Blowup Shield get replaced by the lookup, or kept alongside it?
